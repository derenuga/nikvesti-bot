## Головне, що треба знати до початку

**Оновлення PTB САМЕ ПО СОБІ Rich Messages не дасть.** Це не здогад, а звірка
дат:

| що | коли | Bot API |
|---|---|---|
| наш `python-telegram-bot==21.9` | грудень 2024 | **8.1** |
| найсвіжіший PTB **22.8** | 12.06.2026 | **9.6 / 10.0** |
| Bot API **10.1** — Rich Messages | 11.06.2026 | ← на день раніше за 22.8 |
| Bot API **10.2** — `InputRichMessageMedia` | 14.07.2026 | ← після 22.8 |

Тобто станом на 03.08.2026 **жодна випущена версія PTB не вміє
`sendRichMessage`**. Перевірено в коді, а не за документацією:

```python
>>> import telegram; telegram.__version__
'21.9'
>>> hasattr(telegram.Bot, "send_rich_message")
False
>>> telegram.constants.BOT_API_VERSION
'8.1'
```

Отже сесія оновлення має розділити дві задачі, які легко переплутати:

1. **Оновити PTB 21.9 → 22.8.** Дає Bot API 8.1 → 10.0, тобто півтора року
   змін, і прибирає борг. Rich Messages НЕ дає.
2. **Rich Messages — окремо**, поки PTB їх не додасть: прямий HTTP-виклик
   `sendRichMessage` в обхід бібліотеки, локально в тих місцях, де це справді
   потрібно.

Робити (2) без (1) можна. Робити (1) заради (2) — марно.

## План для сесії оновлення

1. **Прочитати changelog 22.0, 22.1, 22.2** — єдина біла пляма цієї розвідки.
2. **Підняти версію в `requirements.txt`, запустити всі тести**:
   `test_promises.py`, `test_promise_eval.py`, `test_entity_increment.py`,
   `test_entity_backfill_filter.py`. Вони не про Telegram, але імпортують
   `handlers/*`, тобто впіймають зламані імпорти.
3. **`python -c "import bot"`** — найдешевша перевірка: bot.py імпортує
   майже всі 40 модулів, і будь-яка зникла назва вилізе одразу.
4. **Прогнати вручну по одній команді з кожного класу**: `/status` (текст),
   `/promises` (HTML + довге), `/promise_export` (документ), `/team` (WebApp-
   кнопка), будь-яка з інлайн-кнопками (`/entity_find`), реакції на пост
   каналу (MessageReactionHandler), пересланий контакт (filters.CONTACT),
   .txt-пакет у приват (filters.Document.FileExtension).
5. **Окремо перевірити Viber-дзеркало** (`viber_mirror.py`): воно смикає
   `bot.get_file()` і працює з `media_group_id` — найтонше місце.

**Деплой:** Railway автодеплоїть із `main`, тож оновлення requirements.txt
одразу піде в прод. Відкату «в один клік» немає — тому спершу переконатись,
що `import bot` і тести проходять локально.

## Rich Messages: що це і чому вони НЕ в цій задачі

**Що дає Bot API 10.1/10.2** (`sendRichMessage`, `InputRichMessage` з полем
`blocks`): заголовки секцій, таблиці, списки, цитати й пул-цитати, колажі,
слайдшоу, роздільники, згортні блоки `details`, формули, карти, футери. Плюс
`sendRichMessageDraft` — стрімінг відповіді частинами.

**Які повідомлення бота переверстувати — питання відкрите і вирішується
окремо, з Олегом.** Спокуса розписати це заздалегідь велика, але список
«ось це в таблицю, а це не чіпати» без погляду на реальний вигляд на
телефоні — здогад. Тендери, документи влади, сплески трафіку, бюджетні
розбори, картка обіцянки, тижневик — усе це кандидати, і жоден не
відсіяний. Тому редизайн повідомлень — **третя сесія**, зі своїм промтом,
і починається вона з розмови, а не з коду.

Ця розвідка потрібна їй лише одним фактом: **оновлення PTB саме по собі
Rich Messages не відкриє**, бо бібліотека зупинилась на Bot API 10.0.
Коли до цього дійде — виклик доведеться робити прямим HTTP-запитом до
`sendRichMessage`, обгорнувши його однією функцією, щоб потім замінити на
нативний метод одним рядком.

Перевірено вже на встановленій 22.8, а не за датами:
`hasattr(telegram.Bot, "send_rich_message")` → `False`,
`telegram.constants.BOT_API_VERSION` → `10.0`.

## Як пройшло оновлення (03.08.2026)

### Біла пляма 22.0–22.2: закрита

| версія | що прибрано / змінено | нас чіпає |
|---|---|---|
| 22.0 | прибрано все, що застаріло у 20.x: `filters.CHAT`, `filters.StatusUpdate.USER_SHARED`, `Defaults.disable_web_page_preview`, `Defaults.quote`, `(get_updates_)proxy_url`, `constants.InlineQueryLimit.MIN_SWITCH_PM_TEXT_LENGTH`, `EncryptedPassportElement.credentials`, аргумент `quote` у `Message.reply_*`, аргументи `*_timeout` у `run_polling`/`start_webhook`; `BaseRequest.read_timeout` став абстрактним | **лише `bootstrap_retries`** (нижче) |
| 22.1 | Bot API 9.0; порядок аргументів `send_gift`; депрекейт `StarTransactions`, `BusinessConnection.can_reply`, `ChatFullInfo.can_send_gift` | ні |
| 22.2 | опт-ін `PTB_TIMEDELTA` — часові поля стануть `datetime.timedelta` у майбутньому мажорі | ні (сьогодні), але див. нижче |

Нічого з прибраного в коді немає — звірено ґрепом по всьому репо, а не на
око: `Defaults` ми не конфігуруємо взагалі, `quote=` у `reply_*` не
передаємо (збіги в ґрепі — наш власний kwarg `quote` у банку тем), проксі не
задаємо, `run_polling` викликаємо з одним аргументом, свого `BaseRequest`
не маємо.

**`disable_web_page_preview` живий.** Це головне, чого можна було злякатись:
параметр застарів ще у 20.8, а 22.0 прибирав саме «застаріле у 20.x», і в нас
його ~70 викликів. Але прибрали лише `Defaults.disable_web_page_preview` —
сам параметр методів на місці й досі мовчки перетворюється на
`link_preview_options={'is_disabled': True}`. Перевірено не документацією, а
перехопленим запитом: під 21.9 і під 22.8 у Telegram їде байт у байт те саме.

### Що таки зачепило нас: тихий дефолт `bootstrap_retries`

Єдина реальна зміна поведінки — і вона не в списку ламальних, бо формально
це не прибирання:

```
21.9:  def run_polling(..., bootstrap_retries: int = -1, ...)   # ретраїти нескінченно
22.8:  def run_polling(..., bootstrap_retries: int = 0, ...)    # не ретраїти взагалі
```

Нею накрито `initialize()` і бутстрап `start_polling` — тобто перші дзвінки в
Telegram при старті процесу. Ми дефолт не перевизначали, тож оновлення тихо
перевело старт бота з «блимання мережі перечекаємо» на «падаємо одразу»: на
Railway кожен деплой підіймає контейнер заново, і мережевий чих у цю секунду
клав би процес до рестарту.

Полагоджено явним значенням у `bot.py` (`bootstrap_retries=5`) з поясненням
у коментарі. Не `-1`: нескінченні спроби ховають справжню поломку (битий
токен висів би мовчки замість голосно впасти), і сам PTB від них відмовився
свідомо.

### Що лишається на майбутнє: `PTB_TIMEDELTA`

З 22.2 часові поля (`Video.duration` тощо) готуються стати
`datetime.timedelta`. Зараз це **опт-ін** через змінну середовища, дефолт —
як був, `int`. Нас це стосується рівно в одному місці:
`viber_mirror._mirror_video` порівнює `v.duration > VIDEO_MAX_DURATION` і
віддає `v.duration` у Viber. Сьогодні працює (перевірено), у логах лише
депрекейт-ворнінг на кожне дзеркалене відео. **Коли PTB увімкне це за
замовчуванням — порівняння впаде `TypeError`.** Кодом не чіпаємо (правити
робоче заради гіпотетичного мажора дорожче, ніж записати), але той, хто
оновлюватиме PTB наступного разу, має почати саме з цього рядка.

### Чим перевірялось

Живого токена в сесії оновлення немає, тому ручний прогін зроблено офлайн:
підмінено ТІЛЬКИ транспорт (`BaseRequest`), а весь PTB — розбір `Update`,
фільтри, реєстрація 175 handlers, серіалізація параметрів, `reply_markup`,
`InputFile` — працює справжній. Прогнано під 21.9 і під 22.8, вивід
**побайтово однаковий**:

- `/status` (текст) · `/promises` (HTML + довге, `edit_text`) ·
  `/promise_export` (документ) · `/team` (WebApp-кнопка) · `/entity_find`
  (інлайн-кнопки) · тап по кнопці (`answerCallbackQuery`);
- реакція на пост каналу (`MessageReactionHandler`), пересланий контакт
  (`filters.CONTACT`), .txt-пакет у приват
  (`filters.Document.FileExtension` + `get_file` + завантаження), пост у
  канал (`filters.ChatType.CHANNEL`).

Окремо `viber_mirror` (найтонше місце): текст · фото з підписом · відео ·
довге відео → текстовий фолбек · альбом із трьох фото → ОДИН пост.
Головне, що там перевірялось — `File.file_path` після `bot.get_file()` і далі
приходить ПОВНИМ https-URL із токеном (ми віддаємо його Viber посиланням на
медіа); якби PTB перестав добудовувати базовий URL, кожне фото мовчки падало
б у текст.

Плюс `python -c "import bot"` і тести: `test_promises.py` 200/200,
`test_promise_eval.py` 28/28, `test_entity_increment.py` 15/15,
`test_entity_backfill_filter.py` 9/9 — і решта наборів репо (ролі 229/229,
сміття 104/104, матчинг, KPI, сповіщення) теж зелена. Не запускались лише
ті, що потребують живих ключів Facebook, і webapp-тести на playwright — до
PTB вони не мають стосунку.

### Залежності

Голий `python-telegram-bot==22.8` тягне лише `httpx>=0.27,<0.29` — усе інше
(APScheduler, cachetools, tornado) сидить в extras, яких ми не ставимо. Тому
наш власний пін `APScheduler==3.10.4` і `anthropic` з їхнім httpx не
посварились: `pip check` після встановлення чистий.
