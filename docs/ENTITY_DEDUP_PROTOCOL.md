# Протокол розбору дублів сутностей

Домовленість Олега і сесії від 16.08.2026. Писався після того, як я почав
приносити пакети злиття, не домовившись про правила, і двічі назвав здогад
фактом («правильне написання — Димитрова», «правильне — Еммануель»). Обидва
рази підстави не було жодної.

Протокол існує, щоб таке не повторювалось, і щоб робота йшла хвилями, а не
пачками по п'ятнадцять пар навмання.

---

## 1. Правила

**1.1. Схожість написання — це привід шукати доказ, а не доказ.**
Вона не відрізняє «Віткофф / Віткоф» (одна людина) від «Харченко / Марченко»
(двоє різних). Злиття — лише коли встановлено, що це один об'єкт.

**1.2. Сила доказів, згори вниз:**

| | Доказ | Приклад |
|---|---|---|
| 1 | Першоджерело: сайт органу, документ про призначення, офіційна сторінка | сайт міськради |
| 2 | Наш текст, де ім'я стоїть біля документа | «згідно з розпорядженням…» |
| 3 | Збіг посади + органу + періоду | Дмитрова: те саме управління, ті самі посади, півтора року паралельно |
| 4 | Спільні статті (співпоява) | двоє згадані в одному матеріалі |
| 5 | Сама лише схожість написання | **не доказ** |

**1.3. Яке написання лишається — вирішує першоджерело, а не кількість згадок.**
Не знайшли — не гадаємо: лишаємо згадуваніше і кладемо в список «уточнити
написання». Кількість згадок каже, як частіше ПИСАЛИ, а не як ПРАВИЛЬНО.

**1.4. Перед рядком у пакеті — сходити й перевірити.** Google, сайт органу,
сторінка установи. У кожному рядку пакета — підстава, звідки взято.

**1.5. У пакет ідуть ЛИШЕ стопроцентні.** Спірне не їде «до купи» — воно йде
окремим списком питань, до кожного доказ і посилання.

**1.6. «Різні» треба пам'ятати.** Інакше наступний прогін принесе ті самі пари.

## 2. Класи дублів (з живих даних, 16.08)

**Зливаються впевнено:**
- транслітерація іноземних імен: «Марко / Марк Рубіо», «Віткофф / Віткоф»;
- своя одруківка: «Серій Сухомлин» (15 згадок!);
- відмінок замість називного: «Ярослава Железняка», «Олександра Герасименю»;
- порядок слів: «Бєрестнєв Борис Валентинович» / «Борис Валентинович Бєрестнєв»;
- форми імені: «Євгеній / Євген».

**Ніколи не зливаються автоматично:**
- схожі прізвища різних людей: Харченко / Марченко / Ларченко, Кличко /
  Клочко, Гончаренко / Гончар, Мельничук / Мельник;
- голі імена («Олександр», «Катерина», «Петро») — це не дублі, а СМІТТЯ
  витягу: під одним іменем злиплись десятки людей, а поруч живуть історичні
  особи («Олександр II»). Матеріал для `/entity_junk`, не для злиття.

## 3. Порядок роботи

1. **Замір.** Скільки кандидатів, по класах, окремо `person` / `org` / `place`.
   Числа, без жодного злиття.
2. **Пакет №1 — лише безсумнівний клас.** Транслітерація, одруківки, відмінки,
   порядок слів. Із підставою в кожному рядку.
3. **Прогін і звіт.** Що злилось, скільки згадок зачеплено, чи не поїхало
   щось стороннє.
4. **Спірне — списком питань**, по одному, з доказами.
5. **Сміття** — окремо, через `/entity_junk`.

**Розподіл праці:** очередь генерує БОТ своїм детектором (`/entity_classes`,
`/entity_scale`) — у сесії другий детектор не пишемо, інакше буде два пороги і
вічне «чому числа не сходяться». Сесія через MCP приносить ДОКАЗИ по конкретній
парі (ролі, періоди, спільні статті). Рішення — людина. Незворотну дію робить
бот, у якого є журнал і відкат.

**Порядок хвиль.** Сутності є лише в 10% архіву (29 400 статей із 291 233).
Чистимо СПОЧАТКУ ядро — картки з багатьма згадками: кожне «так» лягає правилом
у `entity_merge_rules`, і наступний витяг цей дубль уже не створить. Тобто
чистка зараз працює як щеплення для решти 90%. Друга хвиля — після бекфілу.

## 4. Що знайшлось при написанні протоколу

**Злиття рвало банк тем.** Полагоджено 16.08, є тест
`test_entity_merge_promises.py`. Злиття перевішувало зв'язки зі статтями,
правила й орган канону ролей — усе, що існувало на момент його написання. Банк
тем зʼявився пізніше, і його ніхто не догнав, хоча він тримає три посилання на
картки (`commitments.subject_entity_id`, `owner_entity_id`,
`commitment_objects.entity_id`). Програшна картка ВИДАЛЯЄТЬСЯ — і обіцянка
лишалась із посиланням у нікуди: зникала з пошуку `/promises` по сутності, а
детектор виконання переставав шукати для неї новини (його пре-фільтр працює
саме за спільною карткою предмета). Мовчки, без помилки на екрані.

Перевірено на живому Postgres: без фіксу 5 перевірок із 10 падають, зокрема
«обіцянка з посиланням у нікуди — 1».

## 5. Що лишається зробити

**5.1. Пам'ять «ні, різні» для карток** — таблиця за зразком `role_pairs`
(вона вже є для ролей і працює саме так). Формулювання Олега: «у сутності A
має бути пояснення, що це не B, і навпаки». Інженерна поправка: зберігати
ОДНИМ рядком на пару (канонічний порядок id), читати з обох боків — дві
записи про один факт колись розійдуться. Обов'язкове поле — ПРИЧИНА словами
(«різні прізвища», «перевірено по сайту міськради»): через рік «просто різні»
нічого не пояснить.

**5.2. Профілактика — щоб дублі не заводились.** Зараз при записі
(`entity_pipeline.find_or_stage`) нове написання чіпляється до наявної картки
трьома шляхами: точний збіг норми, правила злиття (пам'ять «так»), обчислений
ключ. Але ключ є лише для `org` (без правової форми) і `place` (з розкритим
скороченням); для `person` `loose_key` повертає `None`. Тобто нове написання
прізвища ЗАВЖДИ створює нову картку.

Що можна:
- **ключ на порядок слів** для людей — механічно й безпечно;
- **кандидат-лінк при записі**: нова картка, схожа на наявну, одразу
  реєструється в черзі з контекстом (стаття, посада, орган) — не зливається, а
  показується людині, поки стаття свіжа;
- **правка промпту витягу**: просити називний відмінок і повне ім'я — це
  лікує в джерелі два класи одразу (відмінки й голі імена).

Чого НЕ робити: нечіткого злиття людей за схожістю. «Гладу / Гладун», «Кара /
Карая», «Кличко / Клочко» — різниця в одну букву, і вона несе сенс. У
організацій різниця СИНТАКСИЧНА (форма власності, лапки), і там ключ
безпечний; у людей вона ОРФОГРАФІЧНА, і там автоматика склеює різних людей
незворотно.
